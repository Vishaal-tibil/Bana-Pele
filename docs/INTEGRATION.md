# Integration guide: the network operator's side

How the Naledi backbone connects a partner backend (My Journey's demo server)
to the real Beckn network. The partner-facing documents are
[PARTNER-CONTRACT.md](PARTNER-CONTRACT.md) (the exact formats) and
[partner-kit/README.md](../partner-kit/README.md) (the drop-in kit and quickstart).
This file is for whoever runs the network. Start with the [root README](../README.md) if you are new.

## Quick start (three commands)

Run these in WSL (Windows), or any Linux/macOS shell with Docker, from the repository root.

```bash
./setup.sh              # once: checks Docker, gets the starter kit, installs our apps,
                        #       makes the one routing change it needs, creates a strong API key
./start.sh --tunnel     # starts everything and opens a public https URL (no account needed)
                        #   prints: Public API URL + API key
./connect.sh https://<their-backend>/api/v1     # after they deploy: connects and checks the link
```

(If a script says "permission denied", run it as `bash setup.sh`, `bash start.sh --tunnel`, and so on.)

What to give the My Journey team, privately: the **Public API URL**, the
**API key**, the `partner-kit/` folder and `PARTNER-CONTRACT.md`. They copy the
kit into their Express app, set two environment variables, deploy, and send back
their address. Then `./connect.sh` does the rest.

| Command | What it does |
|---|---|
| `./setup.sh` | one-time prerequisites; safe to re-run |
| `./start.sh [--tunnel]` | start the network (`--tunnel` adds the public URL, which changes each start) |
| `./connect.sh <address>` | point the network at their backend and run `./check.sh` (`--off` disconnects) |
| `./check.sh` | our side, their two endpoints, and a real search through both adapters |
| `./stop.sh` | stop everything (saved state is kept) |
| `./start.sh --reference` | also run the reference partner app and connect to it (for testing) |

The API key lives in `~/starter-kit/generic-devkit/install/.env` (created by
`setup.sh`, never committed). A new tunnel URL means sending them the new
address; the key stays the same.

## Shape

```
partner backend (Cloud Run)
   |  REST + X-Api-Key            ^  events (webhook) + match lookup
   v                              |
[edge :3010]  only /v1/*  ->  sandbox-bap (buyer translator)   sandbox-bpp (provider translator)
                                    |  Beckn via onix-bap             ^  Beckn via onix-bpp
                                    v                                 |
                              onix-bap  <-- signed messages -->  onix-bpp        redis
```

- `sandbox-bap` = `frontdoor-bap-server.js` + `v1-bap.js`: the `/v1` API, one
  record per search, events to the partner.
- `sandbox-bpp` = `backbone-bpp-server.js` + `v1-bpp.js`: asks the partner who
  matches, guards needs against double reservation, sends offers, applies the
  partner's decisions.
- `netlib.js`: the state store, event outbox (ordered, retried, survives restarts),
  HTTP helpers. `db.js`: PostgreSQL (see [DATABASE.md](DATABASE.md)).
  `logger.js`: structured JSON logs (see [LOGGING.md](LOGGING.md)).
- `naledi-db` (PostgreSQL 16, internal only): databases `naledi_bap` and `naledi_bpp`.
- `edge` (Caddy, port 3010, loopback only): the only thing to tunnel. It passes
  `/v1/*` to the buyer app and answers 404 to everything else, so the built-in
  page's open routes, the adapter webhook and the adapters stay internal.
- `tunnel` (Cloudflare quick tunnel, profile `tunnel`): the public URL for the edge.
- The built-in Naledi/provider pages (`http://localhost:3001/live`) still work.

## The provider-first offer (design decision)

Beckn discovery starts from the seeker, so WeHelp's proactive offer is modelled
as a **second `on_discover` on Naledi's own search** (her standing intent). The
adapters accept it, including after the request's 30-second TTL (verified at
35 s+; longer gaps not tested). The offer therefore exists only because she has
an intent on the network, and only fields she shares go into it.

## Configuration

`./setup.sh` and `./connect.sh` manage `install/.env`; you rarely edit it. The
variables (also settable in the shell for a single run):

| Variable | Default | Purpose |
|---|---|---|
| `API_KEY` | generated by `setup.sh` | key the partner sends in `X-Api-Key` (and that we send them) |
| `MATCH_URL` | empty | partner's `GET /network/match`. Empty = use the built-in providers. |
| `EVENTS_URL` | empty | partner's `POST /network/events`. Empty = events are recorded only. |
| `EVENTS_API_KEY` | same as `API_KEY` | key we send to the partner |
| `MATCH_TIMEOUT_MS` | 3000 | how long we wait for the match lookup |
| `WAIT_FOR_REQUEST_MS` | 4000 | how long `decision`/`complete` wait for the request to arrive |
| `OFFER_MESSAGE_ID` | `new` | fresh message id for offers (`reuse` also works) |
| `DISCOVER_TTL` | `PT30S` | TTL on the search context |
| `BAP_ID`, `BPP_ID`, `NETWORK_ID` | sandbox identities | identity is config; keys stay in the adapters' yaml |
| `BAP_DATABASE_URL`, `BPP_DATABASE_URL` | the local `naledi-db` | each app's PostgreSQL database (`DATABASE_URL` inside the container) |
| `PG_POOL_MAX` | 3 | database connections per app |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn` or `error` |

## State

- PostgreSQL, one database per app: `naledi_bap` (searches, outbox) and
  `naledi_bpp` (provider directory, needs, pending requests, outbox). They
  survive `docker restart`, a hard crash, and `./stop.sh` / `./start.sh`.
  Tables, settings and the Azure steps are in [DATABASE.md](DATABASE.md).
- Without `DATABASE_URL` the apps fall back to the old JSON file (`STATE_FILE`).
- Every message in and out and every state change is logged as JSON, per
  transaction ([LOGGING.md](LOGGING.md)). `GET /v1/log/{transactionId}` returns
  both sides' entries from the database.
- `POST /v1/admin/reset` wipes both sides and bumps the epoch.

## Verification (from our side)

Everything below was run on the final code, starting from a brand-new clone of
the Beckn starter kit and using only `./setup.sh` and `./start.sh`.

| Test | Result | What it covers |
|---|---|---|
| `tests/e2e.js` (standalone) | 88/88 | authentication, matching and non-matching searches, concurrent searches, offers, select/decision/confirm/complete, duplicate reservation (four ways, including two at the same instant), decline then retry, restart of both apps mid-request, the edge exposing only `/v1`, the built-in pages, and the ONIX adapters' logs (no errors, no schema rejections, nothing leaves our network, adapters never restarted) |
| `tests/e2e.js --delegated` | 98/98 | the same, plus events delivered to a partner webhook through failures, an outage and a restart with none lost or duplicated, and a slow partner lookup |
| `tests/partner-flow.js` (local) | 32/32 | the whole script-1 story through the reference partner app built with the kit, and the partner app carrying on when the network is unreachable |
| `tests/partner-flow.js` (public) | 35/35 | the same with every hop over the public internet and TLS: their app behind one Cloudflare tunnel, ours behind another, joined with `./connect.sh` |
| `./check.sh` | passes | after a cold start and after `./connect.sh` |

```bash
API_KEY=<key> node tests/e2e.js                # stack from ./start.sh
API_KEY=<key> node tests/partner-flow.js       # stack from ./start.sh --reference
```

Two real problems were found and fixed by these tests: a race in which a network
event arrives before the response of the call that caused it (the contract now
tells the partner to send their own `offerId`), and a cold-start race in which
`start.sh` returned before the adapter was listening (it now waits).

## Not verified yet

- Their real backend (only the reference app built from the kit has been used).
- The partner's real API definition beyond the two endpoints in the contract.
- Real network identities: everything still signs as the shared sandbox
  `bap.example.com` / `bpp.example.com`.
- Partner-side persistence (their server is in memory).
- Cloudflare quick tunnels are for demos: the URL is random and changes on every
  start, and there is no uptime promise.
- The adapters log a `payloadstore: duplicate message_id` warning on ordinary
  replies (shared Redis, replies reuse the request's id). Harmless; present
  before this work.
